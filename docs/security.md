# Security and resource model

**Status: implemented local provider controls are identified below; broader protections remain proposals and acceptance constraints.** The specific certificate, enrollment, vault, and delegation mechanisms below remain candidates. The [vision](vision.md) requires explicit authority and execution location. The Alloy MCP interface, CLI, and SDK must not bypass those boundaries.

## Trust boundaries and threat model

Protect one user's server from other users, compromised or overprivileged nodes, network observers, accidental repository leaks and lost node credentials. The server host's administrator, an attacker with server-process access, and trusted in-process Go code can generally read or use server resources: encryption at rest does not protect an unlocked vault from them. A privileged host runner can execute code on its host and must be treated accordingly. This design does not claim to sandbox hostile code, prevent authorized nodes from exfiltrating data they legitimately receive, or protect an already compromised endpoint.

Default bind to loopback/local socket. Remote exposure is an explicit setup action with TLS, authentication, authorization, firewall guidance and visible status. A tunnel does not replace authentication. No administrative access, secret value, connection string or host environment is granted just because a node is registered.

The Go SDK currently exposes a health check, local node sessions, and explicitly registered native HTTP provider connections. Provider access requires a registered bearer token and a matching provider grant; each request checks expiry/revocation. Supplied credentials also authenticate node handshakes, while anonymous handshakes retain no provider authority. A node name is untrusted metadata, not identity or authority. Browser-origin access is rejected, but loopback alone is not authentication: other local processes can connect. There are no administrative HTTP endpoints. See [implemented provider boundaries](server-structure.md#implemented-provider-connections); remote access still requires verified server identity and TLS.

Current client tokens are operator-provisioned, stored as hashes in memory, and must not be reused across servers. `RevokeClient` prevents future admissions but does not undo/cancel in-flight requests or terminate the handshake-only session. Zero expiry lasts until revocation/process exit; persistent enrollment, automatic renewal, and per-provider token issuance remain future work. Same-user processes may steal client tokens; this local slice is not a hostile-code isolation boundary.

OpenAI's explicit login integration supports hidden API-key entry or its documented local/open-source ChatGPT-plan OAuth flow. It validates PKCE/state, signed issuer/audience/expiry/nonce and account identity, and granted plan scopes before saving. Stored token sets are encrypted with an OS-credential-store key, replaced atomically, and refreshed under a cross-process lock; no plaintext fallback or automatic browser launch occurs at normal startup. Encrypted persistence now uses the shared `internal/credentialstore` engine; the public [`credentials` package](../credentials/README.md) exposes opaque locked records with explicit server/integration/account namespaces for custom integrations. OpenAI preserves its legacy user-profile/account-scoped storage and does not gain automatic per-server isolation from this extraction. This is not a full vault or a production security review. Same-user/server compromise can still use unlocked credentials; login eligibility and live account access were not verified during implementation. See [setup and limitations](server-structure.md#openai-login-and-the-minimal-example).

## Principals, enrollment and authorization

See [Authentication and sandboxing](research/auth-and-sandboxing.md) for the proposed low-friction runner/profile flow and execution modes. An administrator may approve a bounded delegation policy once, allowing an authenticated runner to request server-issued credentials for new nodes within that policy without per-node prompts. This does not remove instance authentication or per-operation authorization. The direct enrollment flow below is one proposed remote setup path, not a requirement to manually enroll every runner-managed node.

Each server has a generated stable instance ID and TLS identity, and its own CA or equivalent trusted identity root. An administrator is bootstrapped locally via restrictive OS permissions; remote admin access must be separately configured. A node definition has an ID; each running installation has a distinct revocable credential and instance ID. A host runner is its own principal, not an implicit administrator.

Proposed remote enrollment:

1. An authenticated admin approves a node definition, its manifest digest, requested grants, and target server. The server creates a cryptographically random, single-use, short-lived enrollment token bound to this registration. Display it once; avoid shell arguments, logs and process listings. Offer an interactive pairing code or protected file/stdin; do not place bearer tokens in URLs.
2. The operator starts the node with the server address and **verified server trust**: provision a pinned CA/public-key fingerprint through a separate trusted channel, or use publicly trusted TLS with a verified DNS name. Do not accept a certificate fingerprint fetched from the same unauthenticated connection as proof. Explain first-use fingerprint verification rather than hiding it.
3. Node generates a private key on its host and sends a CSR over the verified TLS channel with the enrollment token. Server atomically consumes the token and issues a short-lived client certificate bound to the server, node and instance. Store keys in OS-protected storage where available and restrictive files otherwise. CSR/token exchange requires rate limits and audit.
4. Thereafter use mTLS plus server-side policy on every operation. Rotate before expiry, revoke lost instances server-side, and re-enroll after expiration; revocation must take effect for existing sessions through disconnect/recheck, not only at next TLS handshake. Clock skew, CA backup/rotation and disaster recovery need an explicit operational procedure before production.

This is a proposed design requiring security review, not a home-grown cryptographic protocol specification. Use established TLS, X.509 and cryptographic libraries. Consider SPIFFE/SPIRE integration for managed deployments later; do not impose its operational cost on a local single-user install.

### Human-authorized devices and purpose-bound workloads

Alloy should distinguish a user's primary machine from a one-purpose automation. A primary-machine helper may be explicitly linked to one or more Alloy servers and offer local integrations (for example, MCP, a credential helper, or a provider-specific proxy). The user may authorize a broad set of capabilities for that device, but this is not ambient authority for every local process: the helper must authenticate to the selected server, enforce the server's grants, and make sensitive local actions and credential exposure visible. "Feels local" describes the interface, not where credentials or execution live.

For a CLI or SDK that can only authenticate with a local credential, there are two honest integration choices: broker supported operations through a local helper so the long-lived upstream secret stays server-side, or deliberately issue/cache a short-lived and narrowly scoped credential on the device. A helper cannot provide direct native CLI compatibility while also guaranteeing that no usable credential ever reaches the CLI. Prefer operation brokering when feasible; make credential materialization explicit, bounded, and revocable when required.

One-purpose workloads (such as a Lambda invocation, CI job, or deployment watcher) should have a separate workload identity and only the grants needed for that task. Prefer platform workload identity/OIDC exchange or instance roles to obtain short-lived credentials. Where those are unavailable, use a unique revocable key per workload with narrow grants, expiry and rotation; do not reuse a human device credential or a static broad key across jobs. These mechanisms are design direction, not implemented support. The existing prototype's shared bearer client token is a local candidate only and does not yet provide workload identity, per-operation grants, or short-lived credential exchange.

Policy defaults to deny and is scoped by server, principal, action and resource/subject, with optional constraints. Examples: `publish:deploy.finished.v1`, `subscribe:deploy.requested.v1`, `resource:deploy-api:deployment.create`, `secret:read:example`, `node:register`. Only the administrator grants privileges; node manifests request them. Subscription, event publishing, payload visibility, resource invocation and administrative operations are separately authorized. Enforce authorization for local, remote and in-process calls; in-process checks are consistency, not a security boundary against malicious Go code. Audit grant changes, registration, credential lifecycle and resource use without recording secrets or payloads by default.

## Resource gateway

Expose narrowly defined operations rather than shipping credentials to every worker:

For provider/harness access, prefer native-compatible connection settings backed by an authorized Alloy gateway over exporting upstream login material; see [resource sharing](server-structure.md#share-access-not-upstream-secrets). Keeping upstream secrets private does not remove delegated authority: a node's Alloy credential can still enable usage, spending, and access to returned data. Scope access by capability, operations/models where enforceable, expiry, revocation, and usage limits. Gateway compatibility and permitted authentication must be verified per integration.

- **Integration/MCP**: server invokes an approved operation using its credential, applies principal/operation policy, timeouts, rate and response limits, records metadata, and returns the permitted result. MCP tools are external code/data: treat tool descriptions and returned text as untrusted, never as authority to override policy. MCP server startup and network access need administrator approval.
- **CLI**: prefer typed adapters or allowlisted command + argument schema. Run on an explicitly named host with restricted environment, working directory, timeout and output size. `aws`/`gh` credentials and profiles are host-specific; do not offer a generic unrestricted shell as a safe resource. Shell metacharacters must not be interpreted when invoking an argument vector. A command with broad credentials still carries broad authority; policy cannot make it intrinsically narrow.
- **Database**: expose preapproved queries/operations or constrained credentials; apply timeouts and result limits. A raw database URL/SQL executor is a privileged escape hatch. Application data storage and Alloy's own metadata store are separate.
- **Secrets/config**: differentiate nonsecret configuration from secret material. Prefer a server-side operation that uses a secret without returning it. Explicit `secret.read` is high-risk, scoped, audited and discouraged; once returned to a node it cannot be recalled. Never promise that environment variables or redaction are fully safe.
- **Future node-provided resource**: node advertises a namespaced operation schema, server admin approves the provider and caller policy, server brokers calls with timeouts and checks, and provider unavailability is surfaced. A node cannot grant itself access or publish a resource that automatically becomes trusted. Defer to after server-local resources work.

### Native connection boundaries

A native gateway can authorize access to a named upstream/account without translating its API. The implemented provider grant covers supported HTTP operations beneath its fixed base URL; it does not enforce model, operation, or spending limits. This is broader authority than an allowlisted operation: such restrictions require protocol-aware enforcement and must not be claimed for opaque forwarding. Preserve native behavior only within the explicitly granted boundary; inspection/filtering and compatibility limits must be visible. A configured upstream and server-side authenticator are trusted; native response bodies are not scrubbed for secrets an upstream itself returns.

Bind upstream authentication to operator-approved destinations. Node-supplied URLs, redirects, headers, or tunnel targets must not turn the gateway into an arbitrary proxy or redirect credential injection. Upstream credentials and Alloy client credentials are different authorities; preserve that distinction on every native protocol path, not only the node session.

Harness compositions reference capabilities but cannot grant them. Supported account-login flows and API-key connections retain separate scopes/entitlements; provider-agnostic clients do not make credentials interchangeable. Future directory/workspace/tunnel access requires explicit host, path or target, read/write authority, and lifecycle semantics—not ambient filesystem access. Those composition and filesystem protections remain design constraints, not implemented features.

## Vault and key lifecycle

Alloy should own the credential lifecycle and a per-server credential namespace; a shared third-party vault should not be required for the single-server case. The current local storage implementation uses an OS keychain/secret service to protect file-encryption keys. Broader deployment backends and headless unlock remain open: possible choices include an explicitly configured platform identity/KMS, protected startup input, or operator-managed key on a headless host. External secret managers can be optional integrations, not an assumed dependency. If Alloy implements a vault, require authenticated encryption with a random data-encryption key wrapped by a protected key or a key derived from a user-supplied passphrase using a vetted memory-hard KDF and unique salt. Document algorithm/version, nonces and associated data, permissions and threat boundaries; do not invent crypto. Never store the wrapping key beside ciphertext unprotected. At-rest encryption applies to vault values, not automatically to event payloads, SQLite, backups, logs or process memory.

For headless startup, require an explicit unlock source (protected FD, OS secret service, external KMS/manager, or operator entry). Automatic unattended unlock necessarily transfers trust to that source/host; do not imply passphrase protection when the passphrase is stored next to the database. Secrets in argv, git, ordinary logs, crash reports and telemetry are prohibited by default. Backups must include encrypted vault data and separately secured recovery keys; test restoration, rotation, revocation and key loss. Prefer short-lived upstream credentials and record which secret version was used without values. Secure deletion from SSDs, copies and logs cannot be guaranteed.

## Security acceptance gates

- Cross-server identity and resource requests fail; an unknown or expired credential fails closed. Revocation terminates existing sessions; token replay fails even under concurrent enrollment.
- Server identity mismatch, bad TLS, unauthorized subject, operation and administrative calls fail, including through local socket and channel adapters.
- Permission changes prompt review; a changed definition cannot silently retain unapproved broader authority. Logs, errors, traces and CLI history tests contain no seeded secret.
- Malicious MCP content cannot grant permissions; CLI argument validation blocks unauthorized command execution. Demonstrate limits of allowed resource output and host-level compromise.
- External security review and dependency/crypto review are release gates for internet exposure. Document residual risks and incident/recovery procedures.
